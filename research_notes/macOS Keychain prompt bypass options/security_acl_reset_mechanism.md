# macOS `security` CLI / Keychain ACL Reset Mechanism on Item Update

> Confidence legend used throughout: **[OFFICIAL]** = Apple documentation/man page; **[EMPIRICAL]** = directly reproduced in this research session (commands given, fully reproducible); **[API-SOURCE]** = inferred from a popular open-source library's source code/comments describing Security.framework behavior; **[COMMUNITY]** = GitHub issue / forum / blog report, not independently confirmed by Apple or by this research's own testing.

## Does `-U` without `-T` officially/documentedly reset the ACL, or is this undocumented/community-only?

### Takeaway
The macOS `security(1)` man page does **not** document any ACL-reset side effect of `-U`; it only documents `-T`/`-A` as controlling the ACL of items being added. Our own direct, reproducible testing on this machine shows the suspected mechanism as literally stated by the user (**plain `security add-generic-password -U` without `-T`, on an item that already exists, wipes the trusted-application ACL**) is **FALSE** on current macOS (tested: Darwin 24.6.0 / macOS Sequoia). `-U` alone preserves the existing ACL untouched. However, a **related but distinct** mechanism — deleting and recreating the item (or calling the ACL-set API explicitly) — does reset the ACL to just the creating binary, and this is very likely what's actually happening in the real-world reports (including Claude Code's own issue tracker).

### Cited Findings
- `man security` (macOS, local, read directly in this session) documents `-T`/`-A` only in the context of `add-generic-password`/`add-internet-password`: *"By default, the application which creates an item is trusted to access its data without warning. You can remove this default access by explicitly specifying an empty app pathname: `-T \"\"`."* It says nothing about what happens to an **existing** item's ACL when `-U` is used without `-T`. **[OFFICIAL]** — man page, read locally via `man security`.
- **[EMPIRICAL]** Direct reproduction performed in this research session on an isolated, disposable test keychain (not the login keychain), to avoid any risk:
  1. Created a keychain, added item with `security add-generic-password -a testacct -s testservice -w secret-v1 -T /usr/bin/true -T /bin/echo test.keychain-db`. Dump showed ACL entry (`decrypt derive export_clear export_wrapped mac sign` — the authorization set relevant to `SecItemCopyMatching`/read) with exactly `applications (2): /usr/bin/true, /bin/echo`, and `cdat` (creation date) = `mdat` (modification date) = `20261014011958Z`.
  2. Ran `security add-generic-password -U -a testacct -s testservice -w secret-v2 test.keychain-db` (no `-T` at all).
  3. Re-dumped ACL: the same ACL entry **still showed both `/usr/bin/true` and `/bin/echo` as trusted applications, unchanged**. `cdat` stayed identical (`20261014011958Z`), confirming this was a true in-place update (not delete+recreate); only `mdat` advanced to `20261014012005Z`.
  - **Conclusion: on this system, `-U` without `-T` does NOT reset the ACL/trusted-application list.** It leaves the previously granted "Always Allow" entries intact.
- **[EMPIRICAL]** Second test on the same item: explicitly ran `security delete-generic-password ...` followed by `security add-generic-password -a testacct -s testservice -w secret-v3 test.keychain-db` (fresh create, no `-U`, no `-T`). Dump showed `cdat` changed to a brand-new timestamp (`20261014012155Z`, proving a genuinely new item), and the ACL's read-relevant entry now listed `applications (1): /usr/bin/security` only — **both previously-trusted apps (`/usr/bin/true`, `/bin/echo`) were gone.** This is the actual mechanism that resets the ACL to "only the creator is trusted."
- **[EMPIRICAL]** Third test: ran `-U` **together with** a (different) `-T /bin/cat` on the item that still had `/usr/bin/true` + `/bin/echo` trusted. This produced `security: SecKeychainItemSetAccess: User canceled the operation.` and a secondary `SecKeychainItemCreateFromContent: The specified item already exists` log line, and the ACL was left unchanged (still `/usr/bin/true`, `/bin/echo` only — the `-U -T` attempt did not apply). This shows that **combining `-U` with any `-T` makes the CLI call `SecKeychainItemSetAccess` to explicitly rewrite the ACL**, which (in an interactive GUI session) would surface an authorization dialog to the user; in this non-interactive sandbox it auto-failed as "canceled." Plain `-U` alone (no `-T` argument at all) never triggers this call, which is why it silently preserves the ACL.
- **[COMMUNITY]** `jchan023/btwb-mcp` issue #17 independently reports the same conclusion from the opposite direction: *"`-U` updates an existing item in place and leaves its ACL untouched... if a keychain item was created before the `-A` flag was added, the restrictive ACL is never replaced, and `-A` has no effect no matter how many times it is passed."* Their fix was to switch to delete-then-add specifically **so that** the ACL would be reset/reapplied — i.e., they identify delete+recreate as the way to *force* an ACL change, and plain update as the way the ACL is *preserved*. — [Issue #17](https://github.com/jchan023/btwb-mcp/issues/17). Note: the reporter caveats they "did not inspect the ACL directly before and after," so treat as corroborating but not itself primary; our empirical test above independently confirms their inference.

### Inferences
- The user's stated hypothesis ("`-U` without `-T` resets the ACL") is the **wrong specific mechanism**, at least on current macOS — but the **category of bug is real**: something in the write path is resetting the ACL, and the most likely candidate per both our own experiment and corroborating evidence (see next section's `99designs/keyring`/`gosnowflake` finding) is that the writer is either (a) deleting and recreating the item rather than updating it in place, or (b) explicitly calling an ACL-setting API/flag (`SecKeychainItemSetAccess`, or CLI `-T`/`-A`) on every write.
- Because the investigated tool was confirmed via `strings` to shell out literally to `security add-generic-password -U ...`, the next concrete step to confirm root cause for *that specific tool* is to determine, from its actual invocation (not just the `-U` flag's presence), whether it also deletes the item first, or passes `-T`/`-A` on the update call — both would reproduce the reset even though plain `-U` alone does not.

### Gaps
- Not verified across macOS versions. All empirical testing here was done only on the single machine available (Darwin 24.6.0, "macOS Sequoia" per environment banner). Apple does not document this behavior anywhere found, so there is no guarantee it is stable across macOS Ventura/Sonoma/Sequoia or future releases — this is reverse-engineered, undocumented behavior that could legitimately change without notice (Apple doesn't promise compatibility for the `security` CLI's internal update semantics).
- Did not obtain Apple's actual `security_tool`/`securityd` source for `add-generic-password`'s `-U` code path (searches for `apple-oss-distributions` source for this specific file did not surface a working source link in the time budget); the empirical black-box test above is a substitute for, not a replacement of, reading the actual implementation.

## Is there a command sequence that avoids the reset when updating an existing item (read ACL, merge, rewrite)?

### Takeaway
Plain `-U` without `-T` is *itself* already the safe sequence — it preserves the ACL by default (confirmed empirically above), so no "read-modify-write merge" is actually needed for the no-op case. But if the *writer* needs to **add** a new trusted app to the ACL (not just avoid touching it), doing so via `-U -T <path>` (or any ACL-setting call) requires explicit authorization and is **not silently scriptable** — classify this as **PARTIALLY VIABLE** for background automation.

### Cited Findings
- **[EMPIRICAL]** As shown above, `-U` with no `-T` argument at all leaves the ACL untouched — this is the "do nothing to the ACL" path, achieved for free, requiring no merge logic.
- **[EMPIRICAL]** Attempting to add/merge a trusted app into an existing item's ACL by calling `-U -T <newpath>` triggers `SecKeychainItemSetAccess`, which failed with "User canceled the operation" in a non-interactive context — meaning in a real interactive session, this would require the user to approve a password/Touch-ID-style authorization dialog. It is **not** a silent, scriptable merge.
- **[OFFICIAL/weak]** `security dump-keychain -a` prints the current ACL (`applications (N): <path> (OK/...)`) for each item, which is the correct read-side primitive to discover "what's currently trusted" before attempting any merge — confirmed directly in this session's test output. `man security` documents `dump-keychain -a` as "Dump access control list of items."
- **[COMMUNITY]** The "solution" in `jchan023/btwb-mcp` #17 for the inverse problem (wanting to *force* a new permissive ACL to apply) was explicitly "Delete-then-add instead of update, so the ACL is set every time rather than inherited" — [Issue #17](https://github.com/jchan023/btwb-mcp/issues/17). This confirms by omission that there is no documented flag that lets you merge trusted apps into an existing ACL without either (a) leaving it alone (`-U`, no `-T`) or (b) fully re-setting it (`-T` list, which requires authorization, or delete+recreate, which wipes prior entries outright).
- **[COMMUNITY]** `set-generic-password-partition-list` (documented in `man security`) is a *separate* ACL-adjacent mechanism — the "partition list," which gates access by code-signing team ID rather than by app path — and explicitly requires the keychain password to change: *"You must present the keychain's password to change a partition list."* This is corroborated by Claude Code issue #81707 (see below), where the partition list (not the trusted-app list) was the actual blocker.

### Inferences
- For the investigated tool's exact failure mode (`-U` without `-T`), **no mitigation is needed on the writer side for the trusted-app-list ACL specifically**, because `-U` alone doesn't touch it — assuming the real-world tool truly only calls `-U` and nothing else (delete, `-T`, `-A`, or `set-*-partition-list`) on the update path. The practical mitigation task is therefore to verify (via `strings`/`dtrace`/process-monitoring on the actual binary, beyond what's described here) whether the write path is pure `-U` or involves a delete+recreate step, since only the latter (per our test) actually destroys the ACL.
- If the goal is instead to proactively *grant* a specific third-party app persistent access without relying on the user clicking "Always Allow," the only script-friendly way (no human authorization dialog) is to pass the full desired `-T` list **at creation time** (before the item exists) — matching the man page's documented behavior and our Test 1. Doing it as a later `-U -T` merge after other apps have already been granted access via GUI "Always Allow" clicks will trigger a fresh authorization prompt, defeating the purpose of a silent merge.

### Gaps
- Did not test whether the authorization-dialog trigger for `-U -T` differs if the *keychain* is already unlocked vs. locked, or whether running as the same user in a real Terminal.app/GUI session (vs. this sandboxed non-interactive shell) produces a normal "Always Allow"-style dialog rather than an automatic cancel. This matters for judging exactly how disruptive a "merge" strategy would be in practice.
- Did not test `security set-generic-password-partition-list` empirically (only read its man-page description) to see whether it can be scripted to merge partitions non-interactively when the keychain password is supplied via `-k`.

## Does the low-level API (SecItemUpdate / SecKeychainItemModifyContent) behave the same as the CLI, or differently?

### Takeaway
The CLI's behavior directly mirrors the underlying API split: **attribute/data-only updates preserve the ACL; explicitly setting access (`SecKeychainItemSetAccess`, or recreating the item) resets it.** This is confirmed both by our CLI-level empirical test and, at the API level, by another open-source credential library's source-code comments describing exactly this distinction. Since the investigated tool shells out to the CLI rather than calling Security.framework directly, the CLI's behavior (now empirically established above) is what actually governs it — the API-level nuance mainly matters for cross-checking *why* the CLI behaves this way.

### Cited Findings
- **[API-SOURCE]** The `99designs/keyring` Go library (used by Snowflake's Go driver, `gosnowflake`) explicitly calls `SetAccess()` on its "standard" write path, which — per the library's own issue discussion — "resets the ACL to the current binary's cdhash" every time. Critically, its `updateItem` function contains a guard comment: *"Don't call SetAccess() as this will cause multiple prompts on update"* — i.e., the library's own maintainers discovered empirically that calling the ACL-setting API on every write causes the exact "Always Allow doesn't stick" symptom, and fixed it by **not** calling `SetAccess()` on updates. — [snowflakedb/gosnowflake issue #1847](https://github.com/snowflakedb/gosnowflake/issues/1847)
- **[COMMUNITY/weak]** General Security framework guidance circulating in forum answers states that changing a `kSecAttrAccessControl`-protected item's access control after creation is not supported via `SecItemUpdate`: *"Calling SecItemUpdate with a new kSecAttrAccessControl won't work... once you set it, you can't change the attribute"* — found via web search aggregation of Apple Developer Forums discussion, not independently confirmed with a primary Apple doc link in this session. **Important scope caveat**: this refers to the newer `kSecAttrAccessControl` (Secure-Enclave/biometric constraint) attribute used mostly on iOS/keychain-items-with-LAContext, which is a **different mechanism** from the classic macOS generic-password `SecAccess`/`SecACL` "trusted application list" that `-T`/`-A` and "Always Allow" dialogs operate on. Do not conflate the two when reading Apple API docs — a lot of search results about `kSecAttrAccessControl` are about the wrong (iOS-style) mechanism for this investigation.
- **[EMPIRICAL, inferred]** Our CLI test's clean separation — plain `-U` (no ACL call) preserves ACL; delete+recreate (forces new `SecAccess`) resets it; `-U -T` (forces `SecKeychainItemSetAccess`) requires authorization — is consistent with the classic macOS `SecKeychainItemModifyAttributesAndData`/`SecKeychainItemModifyContent` (attribute/data update, no access parameter at all) vs. `SecKeychainItemSetAccess` (explicit access-control API) split described generically in Apple's legacy Keychain Services reference. We could not fetch a definitive, current Apple page confirming `SecKeychainItemModifyContent`'s signature lacks an access parameter in this session, but the behavioral test strongly implies it.

### Inferences
- Because the ACL-reset behavior is driven by *which API gets called* (data/attribute update vs. explicit access-set), any tool — whether it uses the `security` CLI or calls Security.framework directly in Swift/ObjC/Go/Rust — will exhibit the same reset-on-recreate / preserve-on-plain-update pattern. The CLI vs. direct-API distinction the user asked about is therefore less important than the create-vs-update-vs-set-access distinction; the investigated Node.js tool shelling out to `security -U` is operating on the "safe" (ACL-preserving) side of that line, *provided* it truly only does `-U` without `-T`/`-A` and without a preceding delete.

### Gaps
- Could not locate current (2024-2026) official Apple documentation explicitly stating the exact signature/behavior of `SecKeychainItemModifyContent` vs. `SecKeychainItemSetAccess` with respect to ACL preservation; Apple's legacy Keychain Services docs for macOS (`SecKeychainItemModifyContent`, `SecKeychainItemSetAccess`) are increasingly hard to find as first-class pages since Apple has been steering docs toward the iOS-oriented `SecItemAdd`/`SecItemUpdate`/`kSecAttrAccessControl` API surface. This is a genuine documentation gap on Apple's side, not just a research-time-budget gap.

## Do popular cross-platform credential libraries document or have open issues about this exact "ACL/Always-Allow reset on update" problem?

### Takeaway
Yes — this is a recognized, recurring class of bug across at least three independent ecosystems (Go/`99designs-keyring`+Snowflake, Python/`keyring`, Node/various CLIs including Claude Code and other MCP tools), though most reports describe the *symptom* (repeated prompts, "Always Allow" not sticking) rather than citing Apple documentation for the *cause* — consistent with this being undocumented, reverse-engineered behavior across the board.

### Cited Findings
- **[COMMUNITY]** `atom/node-keytar` issue #135 (opened 2018): *"I always see confirmation popup on Mac OS (Electron 3) about access to Keychain even if I select Allow always."* — long-standing, unresolved in the archived `keytar` project. — [Issue #135](https://github.com/atom/node-keytar/issues/135)
- **[COMMUNITY]** `jaraco/keyring` issue #144 ("Keychain access control in OS X"): maintainers discuss that keyring delegates to the `security` CLI, so the creating `security` process itself becomes the trusted app; a proposed `-T ""` fix was tested and found to produce ~10 interactive prompts during test runs (including prompts with no "Always Allow" option), and was closed as "wontfix" in Jan 2016 as impractical. This does not confirm the update-reset mechanism specifically but documents the same broader ACL/trust friction. — [Issue #144](https://github.com/jaraco/keyring/issues/144)
- **[COMMUNITY]** A separate, more recent `jaraco/keyring`-ecosystem report (`METR/hawk` issue #1858, title: *"macOS Keychain items are bound to the Python binary that wrote them"*) and general research-summary language found via search: *"keyring creates items with SecItemAdd and no explicit access object, so the item trusts only the creating application, identified by code-signing identity"* — i.e., items created by ad-hoc-signed interpreters (uv/Homebrew Python, venvs) are bound to an unstable identity, so every rewrite looks like a "new" untrusted caller. This is a **different but related** failure mode from the classic "-T/-A/update resets ACL" question: it's about *identity instability*, not about the update call itself resetting anything. Flagging this distinction explicitly since it's easy to conflate the two.
- **[API-SOURCE]** `99designs/keyring` (via `gosnowflake` issue #1847) is the clearest documented case of library authors **knowingly engineering around** the reset-on-`SetAccess` problem, as detailed in the prior section.
- **[COMMUNITY]** Several other current, apparently-unresolved GitHub issues surfaced in this research describing the identical end-user symptom ("Always Allow doesn't stick" / recurring keychain password prompts) in unrelated tools: `rorkai/App-Store-Connect-CLI` #2512, `github/app` #2224 (GitHub's own desktop app!), `steipete/CodexBar` #340, `danswett/agent-ha-bridge` #122, `Sterll/claude-terminal` #230. None of these were opened by this research as primary sources beyond their titles/snippets (not individually fetched in full due to time budget), so treat their specific root-cause claims as **unverified** pending a full read — but their sheer number and cross-tool spread corroborates that this is a widespread, recurring, and still-largely-unsolved class of problem on modern macOS, not a one-off bug in a single tool.

### Inferences
- No library surveyed claims Apple officially documents the reset behavior; every fix found (keyring's abandoned `-T ""` attempt, `99designs/keyring`'s "don't call SetAccess on update" code comment, `btwb-mcp`'s intentional delete+recreate) was arrived at empirically by the library's own maintainers, matching this research's own empirical approach and findings.

### Gaps
- Did not do a full-text read of `rorkai/App-Store-Connect-CLI` #2512, `github/app` #2224, `steipete/CodexBar` #340, `danswett/agent-ha-bridge` #122, or `Sterll/claude-terminal` #230 — only titles/search-snippets were seen. A follow-up pass fetching these in full could strengthen or contradict the "widespread recurring problem" inference, and might surface additional distinct root causes (e.g., the partition-list/team-ID mismatch seen in Claude Code #81707 could apply to some of these too).

## Do the specific Claude Code issues (#88583, #80585, #95822) and other "keychain"/"OAuth refresh token" issues confirm this exact mechanism, or a different one?

### Takeaway
**Refuted for the three cited issue numbers**: #88583, #80585, and #95822 are **not** about ACL/"Always Allow" reset at all — they are about a completely different mechanism, **concurrent/single-use OAuth refresh-token rotation races** that corrupt or blank the stored credential. The ACL-reset-causing-repeated-prompts mechanism the user is investigating **is** real and **is** filed against Claude Code, but under different issue numbers: **#77697** and **#81707** — and even these two describe two distinct sub-mechanisms (plain missing trusted-app list vs. a code-signing-team partition-list mismatch), neither of which is confirmed (nor refuted, standalone) to be specifically "`-U` without `-T`" as opposed to "delete+recreate without `-T`."

### Cited Findings
- **[COMMUNITY/primary]** `anthropics/claude-code` **#77697** ("macOS: Keychain item written without trusted-application list -> auth prompt on every credential read," open as of this research): reporter captured process ancestry showing `claude` spawning `security` directly; created a control item with `-T` that never re-prompted; and — key quote — *"'Always Allow' does not help: Claude Code rewrites/recreates the item, and the new item again has an empty trusted-application list, discarding the granted ACL."* Table of evidence shows prompts resuming exactly when "Claude Code rewrote the item." Suggested fixes, in order: (1) attach `-T` on write, (2) **"Update the item in place instead of delete-and-recreate, so a user-granted ACL survives a token refresh"** (3) honor `~/.claude/.credentials.json` on macOS. Multiple users (`pgaultier`, `tiimonn`, `joshghent`, `parker-g`) confirm the bug persists across versions 2.1.207 through 2.1.246+, calling Claude Code "effectively unusable" on affected machines. Issue remains open (no `closedAt`). — [Issue #77697](https://github.com/anthropics/claude-code/issues/77697)
  - **Important nuance**: the reporter's own language says "rewrites/recreates," not "updates via `-U`" — this is fully consistent with our empirical Test 2 (delete+recreate resets ACL) and does **not**, as written, specifically pin the cause on `-U` alone (which our Test 1 shows preserves ACL). This issue corroborates the *symptom* and a plausible *delete+recreate* cause, but does not itself distinguish "`-U` without `-T`" from "delete, then add without `-T`" as the exact code path.
- **[COMMUNITY/primary]** `anthropics/claude-code` **#81707** ("macOS: Claude Code locks itself out of its own keychain credential," closed 2026-08-15): this is a **different mechanism entirely** from a plain missing trusted-app list. The reporter shows the item's ACL is actually permissive (`applications: <any>`, `don't-require-password`) but the **partition list** (a separate ACL sub-mechanism gating by code-signing team ID, set via `set-*-partition-list`) is hard-set to `teamid:NKUJUXUJ3B` — which matches neither the `security` CLI's required `apple-tool:` entry nor Claude Code's actual signing team `Q6L2SF6YDW`. Every read is blocked by this partition-list mismatch, not by the trusted-application ACL. Quote: *"the partition list is repeatedly reset [on every rewrite]... prompts return indefinitely."* Workaround confirmed by reporter: manually running `security set-generic-password-partition-list -S apple-tool:,apple:,teamid:NKUJUXUJ3B ...` silences it "until the next credential rewrite resets the partition list." Closed same day it was filed (2026-08-15), with a comment thread referencing a related, separately "not planned" issue #62361, and other users (`virtualzone`, `tiimonn`) reporting the app is "almost unusable" because of it. — [Issue #81707](https://github.com/anthropics/claude-code/issues/81707)
- **[COMMUNITY/primary]** `anthropics/claude-code` **#88583** ("credential corruption" — exact title not captured, but body confirms): describes the stored OAuth credential being overwritten with **blanked `accessToken`/`refreshToken` fields** (non-secret fields like `subscriptionType` and `refreshTokenExpiresAt` staying intact) roughly every 1-3 days across 5+ long-lived parallel sessions, requiring full interactive re-login to recover. This is **credential corruption/blanking**, unrelated to ACL or "Always Allow" — a data-race on the credential's *contents*, not its *access control*. References other issues (#84331, #83345, #83834, #43392) reporting the same corruption signature. — [Issue #88583](https://github.com/anthropics/claude-code/issues/88583)
- **[COMMUNITY/primary]** `anthropics/claude-code` **#80585** ("multiple concurrent local sessions race on OAuth refresh-token rotation → near-daily forced `/login`"): explicitly describes Anthropic's refresh grant being **single-use** (rotates the refresh token), so when multiple `claude` processes refresh concurrently, the first succeeds and the others get an `invalid_grant`-class error that **clears the keychain credential**, forcing all sessions to re-login. This is a **refresh-token rotation race condition**, explicitly *not* an ACL/prompt issue — it's about the stored secret value itself becoming invalid/cleared due to a logic race, independent of any keychain permission dialog. — [Issue #80585](https://github.com/anthropics/claude-code/issues/80585)
- **[COMMUNITY/primary]** `anthropics/claude-code` **#95822** ("refresh init starts on every command, abandoned by short-lived commands that `process.exit()` before it lands"): describes a structural race where a short-lived command (e.g. `claude auth status`) starts an OAuth refresh, the server rotates the refresh token, but the process exits before the new token pair is written back to the keychain — leaving a stale, now-invalid refresh token in the keychain for the next process to fail on. Explicitly framed by the reporter as related to, but a different code path from, the already-closed "exit-time refresh not persisted" issue #16957. This is again a **refresh-token persistence/race bug**, not an ACL/trusted-app-list bug. — [Issue #95822](https://github.com/anthropics/claude-code/issues/95822)

### Inferences
- The three issue numbers explicitly named in the task (#88583, #80585, #95822) are a **false lead for the ACL-reset hypothesis specifically** — they are real, well-evidenced bugs, but about single-use refresh-token rotation races and credential blanking, a data-integrity problem, not an access-control/permission-prompt problem. They should not be cited as evidence for the ACL-reset mechanism.
- The correct issues for the ACL/"Always Allow"/repeated-prompt mechanism are **#77697** (plain missing trusted-app list, attributed by the reporter to delete-and-recreate on write) and **#81707** (a related but mechanistically distinct partition-list/team-ID mismatch). Both are filed, both remain inadequately fixed as of this research (per #77697's thread, confirmed still present through at least v2.1.246; #81707 closed same-day but the closure reasoning/fix was not visible in the fetched fields — flagged as a gap below).
- Taken together with our own CLI-level empirical findings, the most defensible overall narrative is: **Claude Code's actual observed bug is consistent with delete+recreate-without-`-T` (issue #77697) and/or a stale partition list (issue #81707) — not with plain `-U`-without-`-T` on an existing item**, since the latter was empirically shown in this research to preserve the ACL. If the Node.js tool under investigation by the user is confirmed via `strings` to call exactly `add-generic-password -U -a ... -s ... -X ...` with no delete beforehand and no `-T`, our empirical result predicts its existing third-party grants should *survive* that specific call — meaning either (a) the tool has a different write path elsewhere (e.g., it also deletes on some code paths, or sets the partition list), or (b) the reset the user is observing is actually the partition-list mechanism from #81707 rather than the trusted-application-list mechanism, or (c) macOS version-specific behavior differs from what was tested here.

### Gaps
- Did not fetch the full comment thread / linked PR for #81707's resolution (it shows `closedAt` but the actual fix applied was not retrieved) — worth a follow-up `gh issue view 81707 --comments` deep-read or `gh pr list --search "81707"` to see exactly what Anthropic changed, which would directly indicate whether they confirmed "delete+recreate" or "partition list" or something else as root cause.
- Did not independently inspect the actual Claude Code CLI binary's `security` invocation sequence (the user says this was already done via `strings` for the tool in question — that confirms the literal `-U ...` command line appears in the binary, but `strings` cannot by itself prove whether a `delete-generic-password` call *also* precedes it in the actual runtime code path, which per our findings is the detail that matters most). Recommend the user re-run their `strings`/process-trace analysis specifically looking for a `delete-generic-password` or `set-generic-password-partition-list` call adjacent to the `-U` call, and/or trace live with `sudo fs_usage`/`dtruss`/Endpoint Security logging to see the actual sequence of `security` invocations around a credential refresh.
- Referenced-but-unfetched related issues (#62361 "not planned", #43392 "fixed for MCP credentials only", #84331/#83345/#83834, #16957) were seen only as cross-references inside the fetched issues, not read directly — could contain additional detail relevant to root-causing the exact mechanism.

## Overall viability classification of mitigations found

- **Reading current ACL before writing, merging, and rewriting with the full `-T` list to preserve existing trusted apps** → **PARTIALLY VIABLE**. It works in the sense that supplying the full desired `-T` set does set the ACL correctly (confirmed at creation time in Test 1), but any such write to an *existing* item that already has entries from prior GUI "Always Allow" clicks invokes `SecKeychainItemSetAccess`, which is authorization-gated (confirmed empirically: "User canceled the operation" in a non-interactive context) — so it cannot be done silently/non-interactively in the background the way a credential-refresh daemon would need. This mitigation is only clean if applied once at first-creation time, before any user has had a chance to grant ad hoc "Always Allow" access via the GUI.
- **Simply using `-U` without `-T` and without deleting first** → **VIABLE**, and per our empirical testing, is already effectively "preserve the ACL" — no merge logic needed. This reframes the user's suspected problem: if the real tool's symptom genuinely matches a pure-`-U` call, the bug is likely elsewhere (partition list, or an undetected delete step), not in the `-U` call itself. This is a finding *for* the user's own mitigation design: don't build a complex read-merge-rewrite pipeline to solve the stated hypothesis, because `-U` alone isn't the culprit — instead, audit for a hidden delete or partition-list write.
- **Switching the write path to the Security.framework API directly instead of shelling out to `security`** → **NOT APPLICABLE as a fix** for a third-party/reader app (it's the writer/`claude` CLI's code, which the user has no control over per the constraints) and, per the API-level evidence found (`99designs/keyring`'s `SetAccess()` comment), **would not even be a different behavior** — the same create-vs-update-vs-set-access distinction applies at the API level as at the CLI level. This is not a reader-side mitigation at all.
- **Reader-side mitigations in general** → **INVIABLE** as a category for this specific problem. Every mechanism found here (delete+recreate, `SetAccess`/`-T` calls, partition-list resets) is entirely controlled by the writer (the `claude`/investigated CLI's own code). A third-party reading app has no API to pin or protect its own ACL grant against being overwritten by another process's write to the same keychain item; the only true fix is upstream, in the writer's code (as Anthropic's own issue #77697 reporter concludes, recommending the writer either attach `-T` on write or stop deleting/recreating the item).
