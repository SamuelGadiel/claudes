# Nenhuma via de privilégio elimina o prompt do Keychain

Não existe, em nenhuma camada investigada, uma forma legítima de a ClaudeS ler o item `Claude Code-credentials` (criado pelo `claude` CLI da Anthropic) sem prompt de autorização de forma **durável**: o Keychain Services do macOS amarra suas ACLs à **identidade de assinatura de código do processo requisitante** (Designated Requirement/CDHash), uma camada ortogonal a UID Unix, a privilégios `sudo`/root, e ao sistema TCC — e um engenheiro de DTS da Apple confirmou textualmente que tentar usar o Keychain para diferenciar processos root "definitivamente vai gerar problemas" ([Apple Developer Forums #737888](https://developer.apple.com/forums/thread/737888)). Rodar como root, criar um LaunchDaemon privilegiado, migrar o item para o System Keychain, ou declarar qualquer entitlement de Keychain Sharing são todos **INVIÁVEIS** para este cenário, porque todos pressupõem que a ClaudeS controla o item ou compartilha o Team ID da Anthropic — nenhuma das duas condições é verdadeira, e a ClaudeS, sendo assinada ad-hoc, nem possui um Team ID real para colocar em qualquer entitlement. O único caminho tecnicamente funcional fora do modelo oficial — automação de clique via Accessibility no diálogo do `SecurityAgent` — não é um bypass da ACL, é automação da resposta humana ao prompt, historicamente associada a técnicas de malware (Patrick Wardle/Objective-See), e substitui N prompts de Keychain por um prompt de TCC mais fragilidade entre versões do macOS. A causa raiz documentada do problema não está do lado do leitor: o próprio `claude` CLI reescreve o item a cada renovação de token OAuth e, nessa reescrita, descarta a ACL/partition list concedida — comportamento confirmado empiricamente nesta pesquisa e registrado como bug aberto no repositório `anthropics/claude-code` (#77697, #81707, #94491). A estratégia defensável para a ClaudeS não é "contornar o prompt", é reduzir drasticamente a frequência da leitura direta do item de terceiro, seguindo o padrão já adotado por ferramentas análogas (CodexBar, Uzzy, Codenotch).

## Privilégio, entitlement e API de ACL: todas as portas fecham na mesma parede

A hipótese mais intuitiva — "rode com mais privilégio e o sistema deixa passar" — não se sustenta em nenhuma variante testada. O prompt "App X deseja acessar a chave..." é resolvido pelo `securityd` com base na **trusted-application list / partition list** do item, vinculada ao Designated Requirement/CDHash do binário chamador, não ao UID Unix que o executa ([TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html); [Apple Developer Forums #737888](https://developer.apple.com/forums/thread/737888)). Isso significa que um daemon root diferente do processo que criou o item é tratado exatamente como qualquer outro requisitante não listado — recebe o mesmo prompt, ou falha silenciosa por "user interaction not allowed" quando não há sessão de UI ([Apple Developer Forums #759976](https://developer.apple.com/forums/thread/759976)). O único exploit documentado que de fato leu o Keychain sem prompt mesmo com SIP ativo e ACLs configuradas foi o **KeySteal (CVE-2019-8526)**, uma vulnerabilidade de dia zero corrigida pela Apple em 10.14.4 ([LinusHenze/Keysteal](https://github.com/LinusHenze/Keysteal)) — sua própria existência como "achado de segurança" é evidência de que, fora de bug, nem root contorna a barreira.

Migrar o item para o **System Keychain** (gravável apenas por root) não ajuda porque o item é criado e mantido pelo CLI da Anthropic, não pela ClaudeS: mesmo lá, a ACL por item continuaria amarrada à assinatura de código do `claude`, e o "sem prompt" do System Keychain só vale para quem o criou ou foi explicitamente listado com `-T` no momento da criação ([scriptingosx.com](https://scriptingosx.com/2021/04/get-password-from-keychain-in-shell-scripts/)). `security unlock-keychain` e `security -i` também não mudam nada: o primeiro só desbloqueia o keychain como um todo (equivalente a inserir a senha de login), e o segundo é apenas um modo de execução que evita expor a senha em `argv`/histórico — nenhum dos dois toca a avaliação de ACL por item ([keith.github.io man page](https://keith.github.io/xcode-man-pages/security.1.html)). E rodar o **app GUI inteiro como root** nunca foi suportado pela Apple: "There's no supported way to run an app as root, where app is defined as something with a GUI that the user launches from the Finder" — a recomendação oficial é isolar operações privilegiadas num helper separado, mantendo a GUI com privilégios normais ([Apple Developer Forums #708295](https://developer.apple.com/forums/thread/708295); [#772674](https://developer.apple.com/forums/thread/772674)).

No plano de entitlements, `com.apple.security.keychain-access-groups` e `com.apple.security.application-groups` só funcionam **entre apps do mesmo Team ID**, reforçado por provisioning profiles assinados pela própria Apple: "Keychain items can be shared only between apps from the same developer" ([Keychain Access Groups Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups)). Como a ClaudeS é assinada ad-hoc, ela não tem nem Team ID válido para declarar nesse entitlement — o caminho está fechado duplamente: a Anthropic não cooperaria, e mesmo que cooperasse, a ClaudeS precisaria de uma conta de desenvolvedor paga, o que contradiz o cenário ad-hoc. Na API, a família `SecTrustedApplication`/`SecAccess`/`SecKeychainItemSetAccess` que permitiria a um processo se auto-inserir como app confiável está **deprecada desde macOS 10.15, sem substituto moderno**: "There is no direct replacement for `SecTrustedApplicationCreateFromPath`. The problem is that this entire concept is deprecated", e mesmo quando ainda funcional, "there's no way for an app from one team to 'donate' a keychain item to an app from another team... without triggering user authentication" (engenheiro de DTS da Apple, [Apple Developer Forums #129911](https://developer.apple.com/forums/thread/129911)). O comando `security add-generic-password -T`/`-A` só define a lista de confiança **no momento da criação** de um item novo; para um item já existente, qualquer alteração via `-U -T` ou `set-generic-password-partition-list` dispara prompt obrigatório de senha/Touch ID, e isso foi reproduzido empiricamente nesta pesquisa (`SecKeychainItemSetAccess: User canceled the operation` em contexto não interativo) e confirmado por um caso real idêntico: um workaround manual com `set-generic-password-partition-list -S apple-tool:,apple:,teamid:NKUJUXUJ3B` funcionou uma vez, mas "this fix is overwritten when Claude Code rewrites the credential" ([anthropics/claude-code #81707](https://github.com/anthropics/claude-code/issues/81707)).

## A reescrita do token pela Anthropic é a causa raiz, não a defesa do leitor

A pesquisa reproduziu empiricamente o mecanismo exato de reset da ACL em uma máquina Darwin 24.6.0 (macOS Sequoia), e o resultado contradiz a hipótese mais comum da comunidade: `security add-generic-password -U` **sem** `-T` preserva a ACL/trusted-application list inalterada — testado diretamente, com `cdat` (data de criação) idêntico antes e depois, confirmando atualização in-place sem reset. O que de fato reseta a ACL para "apenas o criador é confiável" é **deletar e recriar o item**, ou chamar explicitamente `SecKeychainItemSetAccess` (via `-U -T`, que por sua vez exige autorização). Essa distinção é corroborada de forma independente pela biblioteca `99designs/keyring` (usada pelo driver Go da Snowflake), cujo código contém o comentário literal "*Don't call SetAccess() as this will cause multiple prompts on update*" — ou seja, os próprios mantenedores descobriram empiricamente o mesmo padrão e evitaram deliberadamente chamar a API de ACL em updates ([snowflakedb/gosnowflake #1847](https://github.com/snowflakedb/gosnowflake/issues/1847)).

Aplicado ao caso real do `claude` CLI, dois mecanismos distintos (não um só) explicam os prompts recorrentes documentados no repositório `anthropics/claude-code`. O primeiro, issue **#77697**, mostra o item sendo reescrito sem lista de apps confiáveis: "'Always Allow' does not help: Claude Code rewrites/recreates the item, and the new item again has an empty trusted-application list, discarding the granted ACL" — consistente com um delete+recreate no caminho de escrita, não com um `-U` puro. O segundo, issue **#81707** (fechada em 2026-08-15 sem correção visível confirmada), mostra um mecanismo mecanicamente diferente: a ACL do item em si é permissiva (`applications: <any>`, `don't-require-password`), mas a **partition list** — um gate separado, anterior à avaliação da ACL e invisível na UI do Keychain Access — está fixada em um Team ID que não corresponde nem ao `security` CLI (`apple-tool:`) nem ao Team ID real de assinatura do Claude Code (`Q6L2SF6YDW`), bloqueando toda leitura até que o usuário reaplique manualmente `set-generic-password-partition-list`, concessão que "is overwritten when Claude Code rewrites the credential". Uma terceira issue, **#94491**, reforça com evidência de timestamp que é reescrita in-place (não delete+recreate): `cdat` permanece inalterado enquanto `mdat` muda, e ainda assim a ACL é descartada — sugerindo que, nesse caso específico, é a própria chamada de ACL/partition-list (não a reescrita de dados) que zera a concessão a cada refresh. Três issues abertos (`#77697`, `#81707`, `#94491`) tratam exatamente deste problema sem correção definitiva até a data desta pesquisa (2026-10-13), e a conclusão de maior impacto prático é: **nenhuma mitigação do lado do leitor pode proteger uma concessão de ACL contra ser sobrescrita pelo processo que de fato possui e reescreve o item** — a única correção real é upstream, no código da Anthropic.

Vale notar que `kSecUseAuthenticationUISkip` (substituto moderno de `kSecUseAuthenticationUIFail`) não oferece um meio-termo: instrui o `SecItemCopyMatching` a falhar deterministicamente com `errSecInteractionNotAllowed` em vez de exibir o diálogo, mas nunca retorna o segredo sem autorização — é útil para controlar a experiência de falha (ex.: não travar a UI), não para "ler mesmo assim" ([Apple Developer Forums #103380](https://developer.apple.com/forums/thread/103380)).

## Accessibility pode automatizar o clique, mas reproduz uma técnica de malware

Existe uma via indireta, tecnicamente real hoje, que não altera a ACL mas automatiza a resposta humana a ela: usar a permissão de Accessibility para disparar cliques sintéticos que pressionam "Always Allow" no diálogo do `SecurityAgent`, via AppleScript/System Events (`tell window 1 of process "SecurityAgent" to click button "Always Allow" of group 1`, documentado em discussões de automação — [Keyboard Maestro Forum](https://forum.keyboardmaestro.com/t/pressing-the-always-allow-button-on-keychain-permission-dialogs/26903)). TCC (Accessibility, Apple Events, Full Disk Access) é formalmente um sistema de permissão **independente** do Keychain Services — não há nenhum `kTCCService*` equivalente a "Keychain ACL", e conceder Full Disk Access não cobre acesso a Keychain ([HackTricks: macOS TCC Credential & Data Theft](https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-tcc/macos-tcc-credential-and-data-theft.html)) — então essa rota não é "overlap de permissão", é automação de UI. Patrick Wardle (Objective-See) documentou historicamente que "macOS accessibility features include the ability to make mouse-clicks without actually touching the mouse through software", explorado por malware para clicar em diálogos de segurança ([Speaker Deck — Wardle](https://speakerdeck.com/patrickwardle/the-mouse-is-mightier-than-the-sword)). Na prática, isso não elimina fricção de autorização: transforma N prompts manuais de Keychain em 1 prompt manual de Accessibility (TCC) seguido de cliques automatizados — e é estruturalmente frágil, pois depende de nomes de janela/processo do `SecurityAgent` que a Apple pode alterar entre versões do macOS, além do risco reputacional de replicar uma técnica historicamente classificada como ataque. Por isso a classificação é **PARCIALMENTE VIÁVEL**: funciona hoje, mas não é uma base de engenharia sólida para um produto de longo prazo, e não foi validado empiricamente nesta pesquisa contra o macOS Sequoia atual.

## O padrão vencedor do setor é evitar o item de terceiro, não acessá-lo

Observando como ferramentas reais resolvem exatamente este problema, emerge um padrão claro de dois grupos. Gerenciadores de credenciais que **são a origem** do segredo — `aws-vault` (Keychain próprio, credenciais temporárias via STS, [99designs/aws-vault](https://github.com/99designs/aws-vault)) e `gh` CLI (token OAuth próprio sob `gh:github.com`, [cli/cli #13330](https://github.com/cli/cli/issues/13330)) — nunca precisam deste problema, porque criam e controlam seu próprio item desde a primeira escrita. Observadores de terceiros que **leem o estado de outro programa** — o grupo estruturalmente mais próximo da ClaudeS — convergem para minimizar ou eliminar o toque direto no item, em vez de tentar vencer o prompt. **Uzzy** lê via `/usr/bin/security find-generic-password` em vez de `SecItemCopyMatching` direto do próprio binário, porque esse binário do sistema já está na partition `apple-tool:` do item na maioria dos casos, evitando prompt sem abrir um novo caminho de acesso — o próprio autor reconhece o trade-off: "there is no explicit consent step anymore... Any process of the user can already read the item this way; Uzzy does not open a new path" ([aka-cronos/uzzy #89](https://github.com/aka-cronos/uzzy/issues/89)). **Codenotch** vai além e evita o Keychain inteiramente quando a CLI local `claude` responde a um comando de status equivalente a `claude /usage`, reservando a leitura do Keychain apenas para contas sem CLI instalada ([vinzdg/codenotch #129](https://github.com/vinzdg/codenotch/issues/129)). **CodexBar**, por sua vez, documentou falha permanente após rotação de token porque desabilitou deliberadamente a maioria dos prompts interativos (`allowKeychainPrompt=false`) e passou a aceitar "not found" em vez de interromper o usuário repetidamente ([steipete/CodexBar #4257](https://github.com/steipete/CodexBar/issues/4257)) — evidência de que mesmo apps maduros não encontraram solução melhor que "tolerar falha, não insistir no prompt".

Para a ClaudeS, a combinação mais robusta sustentada pelas fontes é em três camadas: primeiro, preferir — quando disponível — um comando local do `claude` que devolva status sem precisar do Keychain, análogo ao `claude /usage` do Codenotch, como fonte primária; segundo, quando essa via não existir, ler via `/usr/bin/security` (padrão Uzzy) em vez de `SecItemCopyMatching` no próprio binário, já que o binário do sistema costuma estar pré-autorizado; terceiro, cachear o resultado obtido num item de Keychain **próprio** da ClaudeS (padrão aws-vault/gh) para reduzir a frequência de releitura do item de terceiro. Nenhuma dessas camadas elimina o prompt quando a leitura do item original de fato precisar ocorrer após um refresh de token da Anthropic — isso permanece fora do controle da ClaudeS enquanto os bugs upstream (`#77697`, `#81707`, `#94491`) não forem corrigidos. A documentação oficial da Anthropic confirma ainda um fallback de arquivo texto-plano (`~/.claude/.credentials.json`, modo `0600`), mas ele é **automático** (ativado quando o Keychain rejeita a escrita, ex. SSH) e não uma opção que a ClaudeS possa forçar deliberadamente; issues reais mostram esse arquivo **não sendo consultado preferencialmente** mesmo quando válido, tornando-o uma dependência frágil e, por ser texto-plano, legível por qualquer processo do mesmo UID sem Touch ID/verificação de assinatura — uma regressão de segurança real ([anthropics/claude-code #77697](https://github.com/anthropics/claude-code/issues/77697); [code.claude.com/docs/en/authentication](https://code.claude.com/docs/en/authentication)). A via documentada e estável para evitar o Keychain por completo é `claude setup-token` + variável `CLAUDE_CODE_OAUTH_TOKEN`, mas resolve um problema diferente (autenticação não interativa com token gerado manualmente pelo usuário, válido por 1 ano, sem conectores/agendamento), não a leitura do estado de uma sessão `claude` já autenticada via `/login` — que é o que a ClaudeS precisa observar.

## Tabela de classificação consolidada

| Caminho investigado | Classificação | Justificativa resumida |
|---|---|---|
| Rodar app/daemon como root ou com `sudo` | **INVIÁVEL** | ACL é por assinatura de código (CDHash), não por UID; DTS da Apple confirma que root não recebe tratamento especial ([#737888](https://developer.apple.com/forums/thread/737888)) |
| GUI app inteiro como root | **INVIÁVEL** | Nunca suportado pela Apple; recomendação oficial é isolar privilégio em helper separado ([#708295](https://developer.apple.com/forums/thread/708295)) |
| LaunchDaemon/XPC privilegiado + Keychain Sharing cross-Team-ID | **INVIÁVEL** | `keychain-access-groups`/App Groups só funcionam dentro do mesmo Team ID, imposto por provisioning profile assinado pela Apple ([entitlement doc](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups)) |
| Entitlement Keychain Sharing com cooperação da Anthropic | **INVIÁVEL** | Exigiria Team ID real (ClaudeS é ad-hoc) e cooperação explícita da Anthropic, que não ocorrerá |
| API `SecTrustedApplication`/`SecAccess`/`SecKeychainItemSetAccess` para auto-registro | **INVIÁVEL** | Deprecada desde macOS 10.15 sem substituto; mesmo funcional, qualquer alteração de ACL cross-identity exige autenticação do usuário ([#129911](https://developer.apple.com/forums/thread/129911)) |
| `security -U -T` ou `set-generic-password-partition-list` em item já existente | **INVIÁVEL** (sem prompt) | Reproduzido empiricamente: dispara `SecKeychainItemSetAccess`, que exige autorização; concessão é efêmera porque a Anthropic reescreve o item |
| `security -T` na **criação** de item novo (próprio da ClaudeS) | **VIÁVEL** | Funciona sem prompt subsequente, mas só é aplicável a um item que a própria ClaudeS cria e controla, não ao item da Anthropic |
| `kSecUseAuthenticationUISkip`/`Fail` | **INVIÁVEL** (como bypass) | Evita o diálogo mas falha com `errSecInteractionNotAllowed` em vez de retornar o segredo — não é leitura silenciosa |
| Migrar/ler via System Keychain | **INVIÁVEL** (neste cenário) | Resolveria apenas se a ClaudeS controlasse a criação do item; como é a Anthropic quem escreve, a ACL por item permanece amarrada a ela |
| `security unlock-keychain` / `security -i` | **INVIÁVEL** | Afeta apenas o estado locked/unlocked do keychain inteiro, não a ACL por item |
| Accessibility/TCC — overlap formal com ACL do Keychain | **INVIÁVEL** | Sistemas de permissão totalmente independentes; nenhum `kTCCService*` cobre "Keychain ACL" |
| Accessibility — clique sintético automatizando "Always Allow" | **PARCIALMENTE VIÁVEL** | Tecnicamente funcional hoje, mas desloca o prompt (1 aprovação de TCC + automação), é frágil entre versões do macOS, e replica técnica histórica de malware (Wardle) |
| Fallback `~/.claude/.credentials.json` (texto-plano) | **PARCIALMENTE VIÁVEL, não recomendado** | Existe mas é automático/não forçável sob demanda, comprovadamente inconsistente quanto à precedência, e expõe o token sem Touch ID/verificação de assinatura |
| `claude setup-token` + `CLAUDE_CODE_OAUTH_TOKEN` | **VIÁVEL, mas resolve outro problema** | Documentado e estável, mas requer token gerado e colado manualmente pelo usuário (1 ano, sem conectores/agendamento) — não é leitura da sessão `claude` já autenticada |
| Ler via `/usr/bin/security` em vez do próprio binário (padrão Uzzy) | **PARCIALMENTE VIÁVEL** | Evita prompt na prática porque o binário do sistema já está em `apple-tool:`, mas não é controlado pela ClaudeS e pode deixar de funcionar se a partition list mudar |
| Preferir CLI local de status em vez do Keychain (padrão Codenotch) | **PARCIALMENTE VIÁVEL** | Elimina a necessidade de leitura na origem quando disponível, mas depende da CLI estar instalada e manter esse contrato de saída não documentado oficialmente |
| Item de Keychain próprio da ClaudeS como cache (padrão aws-vault/gh) | **PARCIALMENTE VIÁVEL** | Reduz frequência de leitura do item de terceiro, mas não elimina o prompt quando a leitura real do item original ocorrer após um refresh de token |
| Contribuir correção upstream no `anthropics/claude-code` | **VIÁVEL a médio prazo, fora do controle imediato** | É a única correção que resolveria a causa raiz; já há 3 issues abertos (#77697, #81707, #94491) sem fix confirmado até 2026-10-13 |

## Conclusão

A busca por uma configuração — privilégio, entitlement ou API — que torne a leitura do item da Anthropic silenciosa e permanente está, por desenho da Apple, fechada: toda via testada reduz a zero a diferença entre "ClaudeS lê com sudo" e "ClaudeS lê sem sudo", porque a avaliação de confiança nunca olha para o UID. O insight mais acionável desta pesquisa não é uma técnica de bypass, mas a localização exata da causa raiz: a reescrita do item pelo `claude` CLI a cada refresh de token (confirmada empiricamente como delete+recreate ou chamada explícita de `SetAccess`/partition-list, nunca um `-U` simples) é o que derruba qualquer concessão de ACL, e isso é um comportamento do código da Anthropic, não uma lacuna de design que a ClaudeS possa compensar do lado do leitor. Isso reposiciona o problema de "como ler sem prompt" para "como minimizar quantas vezes a leitura real precisa ocorrer" — via CLI local como fonte primária (Codenotch), leitura por `/usr/bin/security` quando a CLI não está disponível (Uzzy), e cache em item de Keychain próprio (aws-vault/gh) — combinado com reportar ou acompanhar as issues abertas no repositório `anthropics/claude-code` (#77697, #81707, #94491), já que a única correção estrutural depende de a Anthropic parar de resetar a ACL/partition list a cada renovação.
