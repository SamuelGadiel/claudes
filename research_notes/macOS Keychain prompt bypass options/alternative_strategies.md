# Estratégias alternativas para ler credenciais de outro processo no macOS sem prompts repetidos do Keychain

## kSecUseAuthenticationUI: `Allow` vs `Skip` vs `Fail` — efeito exato na SecItemCopyMatching

### Takeaway
`kSecUseAuthenticationUISkip` (e o equivalente antigo `kSecUseAuthenticationUIFail`) não é uma forma de "ler sem autorizar": é um modo de falhar deterministicamente, sem diálogo, exatamente quando a leitura exigiria interação do usuário. Não existe no Security framework um terceiro modo que leia o segredo sem autorização e sem erro — a hipótese do key question está correta.

### Cited Findings
- `kSecUseAuthenticationUI` aceita três valores possíveis: `kSecUseAuthenticationUIAllow`, `kSecUseAuthenticationUIFail` (deprecated) e `kSecUseAuthenticationUISkip` — [developer.apple.com/documentation/security/ksecuseauthenticationui](https://developer.apple.com/documentation/security/ksecuseauthenticationui) (a página oficial existe e foi localizada; o WebFetch não conseguiu renderizar o corpo da página — provavelmente JS-rendered — então o texto completo não pôde ser citado literalmente desta fonte primária).
- `kSecUseAuthenticationUISkip` instrui o Keychain Services a **pular/ignorar itens que exigiriam prompt de autenticação** em vez de exibir o diálogo — [swift-keychain-kit issue #2](https://github.com/sinoru/swift-keychain-kit/issues/2); confirmado por síntese de busca sobre a doc oficial — [WebSearch summary citando developer.apple.com](https://developer.apple.com/documentation/security/ksecuseauthenticationui).
- `kSecUseAuthenticationUISkip` é aceito por `SecItemCopyMatching`, mas é **rejeitado com `errSecParam`** por `SecItemUpdate`/`SecItemDelete` — [Apple Developer Forums thread #103380](https://developer.apple.com/forums/thread/103380).
- `kSecUseAuthenticationUIFail` é a forma anterior/depreciada do mesmo comportamento (falhar em vez de prompt); PRs recentes de bibliotecas de terceiros migram explicitamente de `Fail` para `Skip` porque `Fail` está deprecated — [tonypine/job-search-hub PR #19](https://github.com/tonypine/job-search-hub/pull/19).
- Sem `kSecUseAuthenticationUIFail`/`Skip`, o comportamento padrão (`Allow`) é bloqueante: o sistema apresenta o diálogo de autenticação e a chamada `SecItemCopyMatching` fica pendente até o usuário responder — [Apple Developer Forums thread #103380](https://developer.apple.com/forums/thread/103380).

### Inferences
- Para o caso da ClaudeS: se o item `Claude Code-credentials` exigir autenticação (por ACL/partition-list não cobrindo o processo chamador), usar `kSecUseAuthenticationUISkip` evitaria o prompt, mas a leitura retornaria `errSecInteractionNotAllowed` (ou equivalente) em vez do segredo — ou seja, o app teria que tratar "sem acesso agora" e não "acesso obtido silenciosamente". Isso é consistente com o padrão observado nos apps de terceiros pesquisados abaixo (CodexBar, Uzzy, Codenotch), que todos relatam exatamente esse comportamento de falha ao tentar evitar o prompt.

### Gaps
- Não foi possível extrair o texto literal da página oficial da Apple (render via JS impediu o WebFetch); a confirmação vem de fontes secundárias consistentes entre si (fóruns da própria Apple e issues de bibliotecas de terceiros), não do texto primário verbatim.

## Daemon privilegiado (LaunchDaemon) + XPC + Keychain Sharing — funciona entre apps de desenvolvedores diferentes?

### Takeaway
Keychain Sharing via `keychain-access-groups` funciona **somente dentro do mesmo Team ID** (todas as apps assinadas pelo mesmo certificado de desenvolvedor). Como o item `Claude Code-credentials` é escrito pelo processo `claude` assinado pela Anthropic (Team ID próprio, confirmado nas issues abaixo), um LaunchDaemon/XPC de um Team ID diferente (o da ClaudeS) **não ganha acesso automático** por esse mecanismo — a ACL do item continua sendo o fator decisivo, não a arquitetura XPC.

### Cited Findings
- "Sharing is restricted to a single development team — apps from different developer teams cannot share keychain items through access groups. Access groups are prefixed by your team identifier" — [Sybr Consulting, iOS Keychain Access Groups: Security Implications and Best Practices](https://sybr.ca/ios-keychain-access-groups-security-implications-and-best-practices/).
- O access group é construído com o prefixo `$(AppIdentifierPrefix)`, que resolve em tempo de assinatura para o Team ID; o mesmo `AppIdentifierPrefix` precisa ser igual entre app e extensão/daemon para compartilhar — [swift-security-skill, keychain-sharing.md](https://github.com/ivan-magda/swift-security-skill/blob/main/swift-security-expert/references/keychain-sharing.md).
- Quando os dois lados não compartilham o mesmo Team ID, toda escrita no keychain falha com `errSecMissingEntitlement` — [swift-security-skill, keychain-sharing.md](https://github.com/ivan-magda/swift-security-skill/blob/main/swift-security-expert/references/keychain-sharing.md); caso real documentado em [opencarwings-ios PR #1 "Fix keychain sharing for builds signed by a different team"](https://github.com/developerfromjokela/opencarwings-ios/pull/1).
- O item real `Claude Code-credentials` no macOS tem seu Team ID gravado na **partition list** do ACL (não no access group clássico de iOS), e as issues reais da comunidade mostram dois Team IDs diferentes envolvidos conforme a build (CLI standalone vs. sidecar do Claude Desktop): `Q6L2SF6YDW` (Developer ID Application: Anthropic PBC, binário assinado) e `NKUJUXUJ3B` aparecendo na partition list gravada pelo item — [anthropics/claude-code issue #81707](https://github.com/anthropics/claude-code/issues/81707). Isso mostra que mesmo dentro da própria Anthropic há inconsistência de partition list entre builds, o que agrava ainda mais o cenário para um terceiro.
- Ferramentas de terceiros reais (CodexBar, Uzzy, Codenotch) constataram que o item é recriado/reescrito pelo `claude`/`security` CLI a cada refresh de token, resetando a partition list para `teamid:<time da Anthropic ou outro>` ou `apple-tool:` apenas — nunca incluindo o Team ID do app de terceiros — [anthropics/claude-code #77697](https://github.com/anthropics/claude-code/issues/77697), [steipete/CodexBar #4257](https://github.com/steipete/CodexBar/issues/4257), [aka-cronos/uzzy #89](https://github.com/aka-cronos/uzzy/issues/89), [vinzdg/codenotch #129](https://github.com/vinzdg/codenotch/issues/129), [anthropics/claude-code #87348](https://github.com/anthropics/claude-code/issues/87348).

### Inferences
- Um LaunchDaemon/XPC próprio da ClaudeS não resolveria o problema de fundo: a barreira não é "a ClaudeS não tem um daemon privilegiado", é "o item pertence ao Team ID da Anthropic e sua ACL/partition list não inclui (de forma estável) nem o Team ID da ClaudeS nem `apple-tool:` de forma persistente". Um daemon root não contorna isso — autorização de keychain por Team ID é "same-team" por design, não "privilégio root supera ACL de app".
- A única exploração observada na prática que **de fato** evita o prompt (não um daemon, mas uma técnica distinta) é ler o item através do binário `/usr/bin/security`, que já está listado no ACL/partition `apple-tool:` do item na maioria dos casos — ver issue da uzzy abaixo. Isso não é "keychain sharing" no sentido formal, é "usar um leitor que o item já autoriza".

### Gaps
- Não encontrei documentação oficial da Apple tratando especificamente de LaunchDaemon + XPC como vetor formal de "keychain sharing" (esse padrão existe tipicamente para App Groups/extensions dentro do mesmo app, não para brokers privilegiados de terceiros); a conclusão acima é inferida a partir das regras de access group/Team ID, que são as mesmas independentemente do processo ser um daemon ou um app em foreground.

**Classificação: INVIÁVEL** (quando o item pertence a um Team ID diferente, como é o caso aqui — Anthropic vs. ClaudeS).

## A CLI `claude` tem modo de armazenamento alternativo ao Keychain, documentado e configurável?

### Takeaway
Existe um fallback para arquivo de texto (`~/.claude/.credentials.json`, modo `0600`) mas ele é **comportamento de fallback automático** (ativado quando o Keychain rejeita a escrita, ex. SSH), não uma opção configurável que o usuário ou um app terceiro possa forçar deliberadamente para evitar o Keychain em uso normal. Não existe variável de ambiente `CLAUDE_CODE_USE_KEYCHAIN` ou equivalente documentada. E, criticamente, issues reais mostram que esse arquivo **não é confiável como estratégia de bypass**: o Keychain continua sendo recriado e tem precedência, tornando o arquivo obsoleto/stale.

### Cited Findings
- Documentação oficial (code.claude.com/docs/en/authentication, seção "Credential management"): "On macOS, credentials are stored in the encrypted macOS Keychain. When the Keychain rejects the write, such as when it's locked in an SSH session, Claude Code stores your login in `~/.claude/.credentials.json` with file mode `0600` instead, the same storage it uses on Linux." — [code.claude.com/docs/en/authentication](https://code.claude.com/docs/en/authentication).
- A mesma página documenta `CLAUDE_CONFIG_DIR`: "If you've set the `CLAUDE_CONFIG_DIR` environment variable, Claude Code keeps the `.credentials.json` file under that directory instead, including the file the macOS fallback writes, and keys the macOS Keychain entry to that directory too" — [code.claude.com/docs/en/authentication](https://code.claude.com/docs/en/authentication). Isto é uma forma de ter *múltiplas* contas/credenciais, não uma forma de desabilitar o Keychain para a conta padrão.
- Não há nenhuma menção, na doc oficial de autenticação, a uma flag/variável para forçar modo texto-plano no macOS fora do fallback automático de SSH/lock. A doc também não menciona `CLAUDE_CODE_USE_KEYCHAIN`.
- Há um mecanismo oficial e documentado para evitar completamente a leitura do Keychain em cenários não interativos: `claude setup-token` gera um OAuth token de longa duração (1 ano) que o usuário exporta manualmente como `CLAUDE_CODE_OAUTH_TOKEN`; a doc explicita que esse comando "does not save the token anywhere; copy it and set it as the `CLAUDE_CODE_OAUTH_TOKEN` environment variable" — [code.claude.com/docs/en/authentication](https://code.claude.com/docs/en/authentication). Isso bypassa o Keychain, mas exige que o usuário gere e cole manualmente o token num local de confiança da ClaudeS (mecanismo "b" da seção de padrões da indústria abaixo), não é uma leitura do armazenamento da CLI.
- Há também `apiKeyHelper`, um script de shell configurável via settings que retorna uma API key — outra via documentada de fornecer credenciais sem tocar o Keychain da CLI, mas voltada para API key, não para o token OAuth de assinatura — [code.claude.com/docs/en/authentication](https://code.claude.com/docs/en/authentication).
- Issue real confirma que, na prática, o arquivo `.credentials.json` **não é consultado preferencialmente** ao Keychain no macOS, mesmo quando válido: "With a valid credentials file in place, the keychain item was deleted. Claude Code recreated it on its own (fresh `cdat`), again with no trusted-application list, and prompting resumed. The file is not consulted in preference to the keychain, contrary to what several community workarounds assume." — [anthropics/claude-code issue #77697](https://github.com/anthropics/claude-code/issues/77697).
- Outra issue mostra o inverso quebrando também: um `.credentials.json` desatualizado "ganha" do Keychain válido em certas condições, i.e., o comportamento de precedência é instável/contraditório entre reports — [edonadei/caliper issue #180](https://github.com/edonadei/caliper/issues/180) *(não verificado via `gh`; tratar como não confirmado, ver Gaps)*.
- Issue mostra outro risco do arquivo texto: setar `CLAUDE_CODE_OAUTH_TOKEN` pode, em alguns builds, disparar a exclusão silenciosa da entrada do Keychain ao sair do processo, por conta de uma lógica de "cleanup" no combinador de backends (Keychain primário → fallback texto-plano) — [anthropics/claude-code issue #37512](https://github.com/anthropics/claude-code/issues/37512) (fonte secundária/engenharia reversa do autor da issue, status não confirmado como bug reconhecido pela Anthropic).

### Risks (análise técnica dos riscos de ter o token em texto plano)
- `~/.claude/.credentials.json` com modo `0600` restringe leitura ao UID proprietário via permissões POSIX — mas **qualquer processo rodando com esse mesmo UID** (ou seja, qualquer app, script, ou malware que o usuário execute, sem sandboxing e sem exigir nenhuma autorização adicional do sistema) pode ler o arquivo diretamente com uma simples chamada `open()`/`read()`. Não há prompt, não há Touch ID/Face ID, não há verificação de assinatura de código do processo leitor — ao contrário do Keychain, que (quando a ACL está correta) valida a identidade/assinatura do processo chamador antes de liberar o segredo.
- Comparado ao Keychain, que criptografa o item em repouso e amarra o desbloqueio à sessão de login do usuário (ou a Touch ID/Face ID quando configurado), o arquivo texto-plano em disco é legível imediatamente após o login do usuário, sem depender de o Keychain estar desbloqueado — elimina uma camada de defesa em profundidade (ex.: disco montado por outro processo, backup incluindo esse arquivo em texto claro, ferramentas de sincronização/indexação acidentalmente capturando o conteúdo).
- Esse é exatamente o mesmo modelo de risco do fallback já usado no Linux e no fallback de SSH do macOS — ou seja, não é um risco hipotético, é o modelo real já em produção para esses cenários, documentado oficialmente pela própria Anthropic.

### Inferences
- Para a ClaudeS: não há um "modo oficial, suportado e estável" de ler o estado de outra sessão `claude` via arquivo texto-plano, de forma deliberada, fora dos fallbacks automáticos (SSH/lock) ou do fluxo manual com `setup-token`. Depender do fallback de `.credentials.json` seria depender de comportamento *não documentado como contrato estável* e, pelas issues, **ativamente inconsistente/quebrado** (não é consultado com prioridade; pode ficar stale; há relatos de deleção indesejada do item do Keychain).

### Gaps
- Não encontrei changelog/release notes do pacote npm `@anthropic-ai/claude-code` mencionando explicitamente uma mudança de comportamento do fallback de credenciais no macOS (não cheguei a abrir o CHANGELOG.md do repositório diretamente por restrição de tempo/orçamento de chamadas).
- A issue `edonadei/caliper #180` não foi verificada via `gh` (apenas via resumo de busca); tratar como pista não confirmada, não como fato.
- Não há confirmação oficial da Anthropic (changelog, doc, ou resposta de maintainer) sobre o bug relatado em `#37512` (deleção do item do Keychain ao usar `CLAUDE_CODE_OAUTH_TOKEN`) — é uma issue de usuário com análise de engenharia reversa do autor, não uma confirmação da Anthropic.

**Classificação: PARCIALMENTE VIÁVEL, e não recomendado.** O fallback de arquivo existe e é real, mas (1) não é documentado como mecanismo ativável sob demanda para esse propósito, (2) é comprovadamente instável quanto à precedência Keychain-vs-arquivo nas issues da comunidade, e (3) introduz o risco de exposição em texto plano descrito acima. A via documentada e estável para evitar o Keychain é `claude setup-token` + `CLAUDE_CODE_OAUTH_TOKEN`, mas essa é uma credencial *gerada e colada manualmente pelo usuário*, não uma leitura do armazenamento da sessão interativa do `claude` já logado — ou seja, resolve um problema diferente (auth não interativa) e não o problema da ClaudeS (observar o status de uma sessão já autenticada via `/login`).

## Como outras ferramentas populares no macOS lidam com isso na prática?

### Takeaway
O padrão dominante entre apps reais que precisam do status/uso do Claude Code (CodexBar, Uzzy, Codenotch) é o padrão (c) descrito no key question: usar um caminho que **evita tocar o Keychain** sempre que uma alternativa funcional existir (CLI local `claude /usage`, ou leitura via `/usr/bin/security`, que já está na ACL do item), e tratar o Keychain como último recurso ou fonte secundária — não (a) "aceitar o prompt como custo normal" nem (b) "duplicar a credencial num item próprio colado pelo usuário". Ferramentas de credenciais "sérias" como aws-vault e gh, por outro lado, resolvem o problema na raiz porque **são a origem da credencial**: criam seu próprio item desde o início, com ACL própria, em vez de lerem o item de outro processo.

### Cited Findings
- **CodexBar** (app de menu bar que mostra uso do Claude Code) tem um modelo de consentimento explícito (`"Allow reading Claude Code's credentials"`, toggle próprio) e um "prompt mode" configurável (`always`, etc.), mas mesmo assim relata falha permanente após rotação de token da Anthropic porque todos os call sites internos passam `allowKeychainPrompt=false` — ou seja, o próprio app desabilitou deliberadamente a maioria dos prompts interativos e aceita falhar/"not found" em vez de interromper o usuário repetidamente — [steipete/CodexBar issue #4257](https://github.com/steipete/CodexBar/issues/4257).
- **Uzzy** documentou que o prompt reaparece porque a *partition list* do item é resetada pela CLI do Claude a cada refresh de token, e propôs como correção ler o item via `/usr/bin/security find-generic-password` — que já está na partition `apple-tool:` do item e portanto não dispara prompt — em vez de ler via `SecItemCopyMatching` direto do próprio binário do app (que exigiria estar na ACL/partition, algo que a Anthropic reseta constantemente). O autor é explícito sobre o trade-off: "there is no explicit consent step anymore... Any process of the user can already read the item this way; Uzzy does not open a new path." — [aka-cronos/uzzy issue #89](https://github.com/aka-cronos/uzzy/issues/89).
- **Codenotch** foi além: a correção pedida não é sobre o Keychain, é **evitar o Keychain inteiramente** quando o `claude` CLI local responde a `claude /usage` — nesse caso o app usa a CLI como fonte de verdade e nem tenta ler/renovar via Keychain para essa conta, eliminando o prompt na origem. Mantém o caminho do Keychain só como fallback para contas sem CLI instalada (ex.: só Claude Desktop) — [vinzdg/codenotch issue #129](https://github.com/vinzdg/codenotch/issues/129).
- **aws-vault**: não lê credencial de outro processo — ele **é** o armazenamento primário. Credenciais IAM de longa duração são guardadas num Keychain próprio (customizável, inclusive em keychain dedicado separado do login keychain), e o aws-vault gera credenciais temporárias via STS (`GetSessionToken`/`AssumeRole`) que expõe à shell/apps — nunca lê um item de keychain criado por outro aplicativo de terceiro — [99designs/aws-vault README](https://github.com/99designs/aws-vault), [tekumara notes/macos-keychain.md](https://github.com/tekumara/notes/blob/main/macos-keychain.md).
- **gh (GitHub CLI)**: guarda seu próprio token OAuth (`gho_*`) no Keychain do macOS (ou libsecret/Secret Service no Linux, Wincred no Windows), também sendo a origem/criadora do item, não uma leitora de credencial de terceiro — [x-cmd.com/pkg/gh](https://www.x-cmd.com/pkg/gh/), confirmado por issue sobre falta de indicação visível do item: "gh stores its OAuth token (gho_*) silently in the system Keychain under gh:github.com" — [cli/cli issue #13330](https://github.com/cli/cli/issues/13330).
- Extensões/terceiros que querem o token do `gh` usam o comando oficial `gh auth token`, que imprime o token via stdout — um **comando expositor documentado**, análogo ao `claude setup-token`/`apiKeyHelper` do Claude Code, em vez de ler o item do Keychain diretamente — [linuxcommandlibrary.com/man/gh-auth](https://linuxcommandlibrary.com/man/gh-auth); risco reconhecido pela própria comunidade: "gh extension install runs someone else's Go program with your gh credentials in scope and should be vetted like any dependency" — [honnibal.dev, Restricting Coding Agents' CLI GitHub Write Access](https://honnibal.dev/blog/locking-down-gh).
- No Linux, quando nenhum keyring (Secret Service) está disponível, o próprio `gh` admite texto plano e avisa explicitamente o usuário: mensagem "Authentication credentials saved in plain text" — [GitHub discussion #8980](https://github.com/cli/cli/discussions/8980) (ver nota de confiabilidade abaixo).
- Padrão de extensões do Raycast: em geral usam fluxo OAuth próprio ou PAT colado pelo usuário, armazenado no Keychain do próprio app/extensão (padrão "b" do key question) — "Raycast extensions communicate with third party services directly through OAuth protocol or personal access tokens, with credentials stored securely in your Keychain" — [raycast.com/faq](https://www.raycast.com/faq); exemplo concreto: extensão "Password Store" permite salvar no Keychain do macOS ou dentro da própria extensão — [raycast.com/afok/password-store](https://www.raycast.com/afok/password-store).

### Inferences
- Existem na prática **dois grupos distintos** de ferramentas, com estratégias correspondentemente diferentes: (1) gerenciadores de credenciais que *são a fonte* (aws-vault, gh, Raycast extensions com OAuth próprio) — padrão (b), criam e controlam seu próprio item desde a criação, sem nunca precisar ler o item de outro programa; (2) observadores de terceiros que *leem o estado de outro programa* (CodexBar, Uzzy, Codenotch — o grupo mais próximo do caso da ClaudeS) — nenhum desses aceita (a) "custo normal"; todos convergem para minimizar/eliminar a necessidade de tocar o item do outro programa, preferindo uma CLI/comando expositor quando disponível, e tratando a leitura direta do Keychain de terceiro como último recurso frágil e sujeito a prompts recorrentes que não podem ser eliminados de forma durável do lado do app leitor.
- Para a ClaudeS, o precedente mais forte é Codenotch: se o `claude` CLI estiver instalado e responder a um comando de leitura de status (equivalente a `claude /usage`), preferir esse caminho sobre o Keychain elimina o prompt pela raiz, ao custo de depender da CLI estar instalada/funcional e manter esse "contrato" (não documentado oficialmente, mas observável) de saída do comando.

### Gaps
- O conteúdo do GitHub discussion #8980 foi obtido via WebFetch (resumo de IA sobre a página), não verificado linha a linha como as issues que confirmei via `gh issue view`; tratar a citação sobre "Authentication credentials saved in plain text" como plausível mas não auditada da mesma forma rigorosa que as demais.
- Não investiguei o caso específico do 1Password CLI (`op`) nem de extensões VS Code compartilhando autenticação (ex.: GitHub Pull Requests extension lendo token do `gh`) por orçamento de chamadas — ambos ficam como lacuna. Pelo padrão geral observado, a expectativa (não confirmada) é que sigam o mesmo padrão (b)/comando expositor, mas isso é inferência, não fato citado.

## Viabilidade de a ClaudeS criar seu próprio item de Keychain para cachear status

### Takeaway
É uma estratégia tecnicamente sólida e alinhada ao padrão (b) observado na indústria (aws-vault, gh, Raycast com OAuth próprio) — reduz a *frequência* de leitura do item de terceiro — mas não elimina o prompt quando a leitura do item original de fato precisar ocorrer, exatamente como o próprio key question antecipa. Ela também não resolve a causa raiz observada nas issues reais (a Anthropic reescreve/reseta a ACL/partition list do item a cada refresh de token), então o prompt pode voltar a cada poucas horas independentemente de cache.

### Cited Findings
- O padrão de item de Keychain próprio, criado pelo app desde o início com ACL/trusted-application controlada por ele, é exatamente o que apps como aws-vault e extensões do Raycast fazem com segredos deles mesmos — [99designs/aws-vault](https://github.com/99designs/aws-vault), [raycast.com/afok/password-store](https://www.raycast.com/afok/password-store). Um item criado dessa forma, com `-T` apontando para o próprio app, não sofre o problema relatado nas issues do Claude Code, porque quem escreve o item e quem lê é a mesma aplicação/Team ID — consistente com a explicação de `keychain-access-groups` (mesmo Team ID) citada acima.
- Nas issues reais (CodexBar, Uzzy, Codenotch), a fonte do prompt recorrente não é a falta de cache — é o fato de que, sempre que a leitura real do item `Claude Code-credentials` ocorre, a ACL/partition list pode já ter sido resetada pela última reescrita feita pelo `claude`/sidecar — [anthropics/claude-code #77697](https://github.com/anthropics/claude-code/issues/77697), [#81707](https://github.com/anthropics/claude-code/issues/81707), [#87348](https://github.com/anthropics/claude-code/issues/87348). Um cache da ClaudeS reduziria quantas vezes essa leitura de fato acontece, mas cada leitura que ocorrer depois de um refresh de token da Anthropic ainda está sujeita ao mesmo risco de prompt.
- Codenotch mostra uma forma concreta de reduzir drasticamente a necessidade de ler o Keychain: usar o `claude` CLI local (quando presente) como fonte primária de status, e reservar a leitura do Keychain apenas para contas sem CLI instalada — [vinzdg/codenotch #129](https://github.com/vinzdg/codenotch/issues/129). Isso é complementar ao cache em Keychain próprio: primeiro evita a leitura, depois cacheia o resultado que for obtido.

### Inferences
- Para a ClaudeS, a combinação mais robusta observada na pesquisa seria: (1) preferir, quando disponível, um comando/CLI local do `claude` que devolva status sem precisar do Keychain (análogo ao `claude /usage` do Codenotch) como fonte primária; (2) quando essa via não existir ou falhar, cachear o resultado obtido do Keychain num item próprio da ClaudeS (Team ID próprio, ACL controlada desde a criação) para não precisar reler o item de terceiro a cada poll; (3) aceitar explicitamente, e comunicar ao usuário, que a leitura periódica e inevitável do item original da Anthropic continuará sujeita a prompt quando a ACL/partition list dele for resetada por um refresh de token — comportamento fora do controle da ClaudeS, documentado como bug aberto e não resolvido em vários relatos (`#77697` aberto, `#87348` aberto) até a data desta pesquisa (2026-10-13).

### Gaps
- Não encontrei nenhum relato de terceiro que tenha implementado e confirmado publicamente o padrão específico "cache em item de Keychain próprio" para o caso do Claude Code (CodexBar, Uzzy e Codenotch descrevem o problema e propõem correções nos próprios repositórios, mas não documentam explicitamente terem adotado um "item de cache próprio" como solução já implantada) — a recomendação acima é uma inferência por analogia com o padrão geral da indústria (aws-vault/gh), não uma confirmação direta de que essa combinação específica já funciona de forma comprovada para o item `Claude Code-credentials`.

**Classificação: PARCIALMENTE VIÁVEL.** Reduz frequência/exposição e seria uma boa prática de qualquer forma (menor acoplamento ao timing do Keychain de terceiro), mas não elimina a causa raiz do prompt recorrente, que está na forma como a própria Anthropic reescreve a ACL/partition list do item a cada refresh de token — um problema fora do controle da ClaudeS enquanto não houver correção oficial (ver issues abertas `#77697` e `#87348`).
