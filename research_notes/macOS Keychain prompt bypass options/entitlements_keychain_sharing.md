# Entitlements & Keychain Sharing Across Different Apple Developer Team IDs

## O que é o entitlement de compartilhamento de Keychain (keychain-access-groups / application-groups), e ele permite compartilhamento entre Team IDs DIFERENTES sem cooperação do outro desenvolvedor?

### Takeaway
**INVIÁVEL.** Tanto o entitlement `keychain-access-groups` (`com.apple.security.keychain-access-groups`) quanto o `com.apple.security.application-groups` (App Groups) só funcionam entre apps assinados pelo **mesmo Team ID** (mesma conta de desenvolvedor Apple), e isso é reforçado por provisioning profiles assinados pela própria Apple. Não existe nenhum mecanismo de entitlement que permita a um Team ID B ganhar acesso a um grupo de keychain pertencente a um Team ID A sem que A explicitamente inclua B num provisioning profile/entitlement controlado por A. Como a Anthropic não vai fazer isso para o ClaudeS, esse caminho está fechado independentemente de qualquer configuração do lado do ClaudeS.

### Cited Findings
- "Keychain items can be shared only between apps from the same developer." — [Keychain Access Groups Entitlement — Apple Developer Documentation](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups)
- "An app's effective keychain access group list is formed by concatenating the list from the `keychain-access-groups` entitlement (if any), the value of the `application-identifier` entitlement, and the list from the `com.apple.security.application-groups` entitlement (if any)" — todos os três componentes dessa lista são derivados de entitlements assinados sob o **mesmo** Team ID/provisioning profile — [Keychain Access Groups Entitlement — Apple Developer Documentation](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups)
- "The system constructs a virtual array of access groups for each app by concatenating keychain access groups from the `keychain-access-groups` entitlement and the application identifier, which is automatically generated as `TeamID.BundleID`... The Team ID prefix on every group identifier, enforced through code-signed provisioning profiles, prevents cross-team access." — [Sharing access to keychain items among a collection of apps — Apple Developer Documentation](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps) (via pesquisa agregada; página fonte confirmada mas conteúdo extraído de cache de busca, ver Gaps)
- "The `com.apple.security.application-groups` entitlement allows access to group containers that are shared among multiple apps **produced by a single development team**." — [Enabling App Sandbox — Apple Developer Documentation (Entitlement Key Reference)](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html)
- "Third-party apps use access groups with a prefix allocated to them through the Apple Developer Program in their application groups" — confirmando que o prefixo de grupo é emitido pela Apple para a conta de desenvolvedor, não é algo que outro desenvolvedor possa simplesmente reivindicar — [Sharing access to keychain items among a collection of apps](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)
- No GitHub issue sobre o próprio Claude Code (#77697), um comentário observa que o Nextcloud Desktop Client (Team ID `NKUJUXUJ3B`, diferente do Team ID do Claude Code `Q6L2SF6YDW`) conseguiu **sobrescrever** (não ler silenciosamente via ACL) o item `Claude Code-credentials` resetando sua partition list — mas isso ocorreu por **colisão de nome de conta/serviço no keychain legado baseado em arquivo**, não por compartilhamento de access group. Isso é uma falha de design do item legado (qualquer processo com acesso de escrita ao keychain pode tentar escrever um item com o mesmo `-s`/`-a`), não um mecanismo de leitura silenciosa autorizado — [macOS: Keychain item written without trusted-application list → auth prompt on every credential read · Issue #77697](https://github.com/anthropics/claude-code/issues/77697)

### Inferences
- Como o ClaudeS é assinado ad-hoc (sem Developer ID, portanto sem Team ID real emitido pela Apple), ele nem sequer teria um Team ID válido para colocar em qualquer entitlement de access group — isso elimina esse caminho duplamente: (1) a Anthropic não cooperaria, e (2) mesmo que cooperasse, o ClaudeS precisaria de um Team ID pago e um provisioning profile, o que contradiz o cenário de assinatura ad-hoc.
- O caso Nextcloud mostra um vetor de risco oposto e relevante para o projeto: qualquer app com acesso de escrita ao keychain legado pode **corromper** (resetar partition list) o item do `claude` CLI por colisão de nome, mesmo sem ser "trusted". Isso é uma ameaça a mitigar, não uma solução a explorar.

### Gaps
- Não foi possível fazer fetch do corpo completo da página oficial "Sharing access to keychain items among a collection of apps" (o WebFetch só retornou o título da página, aparentemente por bloqueio de renderização client-side do site da Apple); a citação foi reconstruída a partir do snippet agregado do mecanismo de busca, que cita a página como fonte. Recomenda-se verificação manual direta no navegador para confirmar o texto exato, embora o conteúdo seja consistente com as demais páginas oficiais citadas (Keychain Access Groups Entitlement, App Groups) que foram obtidas com sucesso.

## Existe API (SecAccess/SecTrustedApplication/SecKeychainItemSetAccess ou equivalente moderno) que permita a um processo se adicionar como app confiável a um item já existente, programaticamente, sem prompt?

### Takeaway
**INVIÁVEL por design.** A família de API que permitia manipular a ACL de um item de keychain (`SecTrustedApplication`, `SecAccess`, `SecKeychainItemSetAccess`) está **deprecada desde macOS 10.15** e não tem substituto moderno — a Apple confirma oficialmente que o conceito inteiro foi abandonado. Mesmo quando essas APIs ainda funcionam (código legado), modificar a ACL de um item para incluir uma nova aplicação confiável **sempre** dispara autenticação do usuário quando a aplicação solicitante não é a que já possui direito de modificação — não há condição (mesmo sendo o "criador" original, no caso de cruzar Team IDs) que permita um processo de outro Team ID se auto-inserir silenciosamente.

### Cited Findings
- "There is no direct replacement for `SecTrustedApplicationCreateFromPath`. The problem is that this entire concept is deprecated." — citação do engenheiro da Apple DTS "Quinn 'The Eskimo!'" no fórum oficial — [SecTrustedApplicationCreateFromPath replacement — Apple Developer Forums](https://developer.apple.com/forums/thread/129911)
- "In recent macOS releases, there's no way for an app from one team to 'donate' a keychain item to an app from another team, or the system, without triggering user authentication." — mesmo thread, mesma fonte — [Apple Developer Forums — thread 129911](https://developer.apple.com/forums/thread/129911)
- Alternativa mencionada no mesmo thread: criar um `SecAccess` com `trustedApplicationList` nulo, o que torna o item acessível por **qualquer aplicação** (sem necessidade de estar na lista) — mas isso remove completamente o controle de acesso granular, é um trade-off de segurança inaceitável para um token OAuth sensível, e ainda assim não resolve itens já existentes sem reescrevê-los (o que, por sua vez, dispara prompt se feito por um processo que não é o "owner" original) — [Apple Developer Forums — thread 129911](https://developer.apple.com/forums/thread/129911)
- "If the application is not in the list of trusted applications, the user is prompted before access is allowed" — confirmação de que a ausência na lista de confiança implica prompt obrigatório, reforçando que não há bypass silencioso — agregado de resultados de busca sobre `SecKeychainItemSetAccess`/`SecAccess` (ver Gaps quanto à página oficial `SecAccess`)
- "Changing ACL after the fact will trigger a user authorisation dialog" — consistente com o comportamento documentado nos issues do Claude Code analisados na seção seguinte — agregado de busca

### Inferences
- Mesmo que o `claude` CLI, ao criar o item, inicialmente colocasse o ClaudeS na lista de apps confiáveis (algo que exigiria cooperação da Anthropic), qualquer renovação de token que reescreva o item (como o `claude` CLI efetivamente faz, ver próxima seção) tende a resetar essa lista — então mesmo uma concessão pontual não seria duradoura sem mudança de comportamento do lado da Anthropic.
- A deprecação de `SecTrustedApplication`/`SecAccess` sem substituto moderno (a API atual `SecItem*`/`kSecAttrAccessControl` não expõe manipulação de ACL de "lista de apps confiáveis" entre processos de terceiros) é, por si só, evidência de que a Apple fechou deliberadamente essa superfície de automação — era usada em malware/ataques de keychain dumping.

### Gaps
- Não foi possível obter o corpo completo da página oficial `developer.apple.com/documentation/security/secaccess` (WebFetch retornou apenas o título); a citação sobre "deprecated" é consistente com o status conhecido documentado no changelog do macOS 10.15 e corroborada pelo post oficial de engenheiro da Apple (thread 129911), mas recomenda-se conferência manual do texto exato de deprecação na página.

## O comando `security add-generic-password -T` ou `security set-generic-password-partition-list` conseguem adicionar um app à lista de confiança de um item JÁ EXISTENTE sem prompt?

### Takeaway
**PARCIALMENTE VIÁVEL apenas para criação de item novo; INVIÁVEL para item já existente sem prompt.** A flag `-T` da `security(1)` só consegue definir a lista de apps confiáveis **no momento da criação** de um item novo. Para um item que já existe — como é o caso do item do `claude` CLI, que é criado e gerenciado por outro binário — tanto `security add-generic-password -U -T` quanto `security set-generic-password-partition-list` **sempre disparam um prompt de autorização com senha do usuário** quando usados para alterar a ACL/partition list de um item existente. Rodar com privilégios de administrador (`sudo`) não contorna isso, porque a autenticação exigida é a do keychain do usuário (ou Touch ID/senha de login), não uma autorização de root a nível de sistema de arquivos.

### Cited Findings
- "The `-T` flag specifies an application which may access this item, and multiple `-T` options are allowed." E quanto a atualizar um item existente: "when using the `-U` flag to update a keychain item with the `-T` flag, you get prompted in the GUI to allow the change and enter your password... The `security add-generic-password` command can't add in Access Control settings to an existing keychain entry. It can add ACL entries at the time it creates a new entry, but can't do so afterwards." — agregado de Stack Overflow / documentação `security(1)`, citado a partir de pesquisa — [security(1) — General Commands Manual](https://ss64.com/mac/security-password.html)
- Confirmação direta e concreta vinda de um caso real idêntico ao do usuário (app de terceiro lendo item do `claude` CLI): "An external integration applied `security set-generic-password-partition-list -S apple-tool:,apple:` to an adapter-managed OAuth item so non-interactive `/usr/bin/security` readers could read the token without GUI prompts" — mas "re-applying the grant requires the user's login password each time (`set-generic-password-partition-list` prompts), which cannot be automated safely" e "When a keychain item is updated, the partition list gets reset to a single `cdhash:<creating-binary>` entry, silently re-breaking external readers" — [keyring provider: macOS prompts for password after every secretspec upgrade · Issue #438 — cachix/secretspec](https://github.com/cachix/secretspec/issues/438)
- Caso documentado no próprio repositório Anthropic, envolvendo exatamente o item `Claude Code-credentials`: workaround temporário funciona, mas é destruído a cada reescrita feita pelo `claude` CLI: `security set-generic-password-partition-list -S apple-tool:,apple:,teamid:NKUJUXUJ3B -s "Claude Code-credentials" -a <user>` — "This fix is overwritten when Claude Code rewrites the credential." — [macOS: Claude Code locks itself out of its own keychain credential → endless password prompts · Issue #81707](https://github.com/anthropics/claude-code/issues/81707)
- O mesmo issue detalha o mecanismo exato: "The partition list is a gating mechanism separate from the ACL... The ACL itself is permissive (`applications: <any>`, `don't-require-password`)... The partition list acts as a hard gate before the ACL is even evaluated... Clicking 'Always Allow' in the prompt modifies the ACL only, not the partition list... The partition list is not visible in macOS Keychain Access UI." — [Issue #81707](https://github.com/anthropics/claude-code/issues/81707)
- Caso adicional confirmando o padrão de reset em cada escrita/renovação de token: "every OAuth token refresh rewrites the `Claude Code-credentials` keychain item in place and drops its ACL... the write operation doesn't preserve the existing `SecAccess` on update." Evidência de timestamps: `cdat` (creation date) permanece inalterado enquanto `mdat` (modification date) muda, provando que é reescrita in-place (não delete+recreate) e, mesmo assim, a ACL é descartada. — [macOS: token refresh rewrites Claude Code-credentials in place and drops its keychain ACL · Issue #94491](https://github.com/anthropics/claude-code/issues/94491)
- Issue correlato confirma colisão de escrita entre apps de terceiros diferentes (reforça risco, não solução): "macOS client modifies another app's keychain item on startup (sets partition list to `teamid:NKUJUXUJ3B`), breaking Claude Code" — [Issue #10976 — nextcloud/desktop](https://github.com/nextcloud/desktop/issues/10976)
- Outro relato técnico equivalente em outro produto (adaptador MCP), mostrando que o problema não é específico do `claude` CLI mas sim do modelo geral do keychain legado: "coding-agent (MCP adapter): keychain secure-storage rewrites reset the item's partition list, wiping external silent-read grants" — [Issue #9562 — earendil-works/pi](https://github.com/earendil-works/pi/issues/9562)

### Inferences
- Mesmo um workaround manual rodado uma única vez pelo usuário (com prompt de senha aceito) é efêmero: a primeira renovação de token do `claude` CLI (que ocorre automaticamente, não é algo que o ClaudeS controla) reescreve o item e destrói a concessão. Portanto, não existe sequência de comandos `security` que resolva o problema de forma permanente sem repetição periódica do prompt — contradizendo diretamente o requisito de "sem prompt repetido".
- `sudo`/privilégios de administrador não ajudam: a autenticação exigida pelo `securityd` para alterar ACL/partition list é vinculada à sessão de keychain do usuário logado (senha de login ou Touch ID), não ao usuário Unix. Rodar como root não elimina esse prompt.

### Gaps
- Não foi encontrada documentação oficial (man page completa) citando explicitamente que `sudo` não contorna o prompt do `security set-generic-password-partition-list`; a inferência é baseada no comportamento consistente relatado em múltiplos issues reais (nenhum relator conseguiu automatizar via sudo) e no conhecimento geral de que a keychain do usuário é protegida por `securityd` independente de privilégio de root — mas nenhuma fonte citou um teste explícito com `sudo` falhando.

## É tecnicamente possível, sob qualquer condição, um terceiro ler silenciosamente (sem prompt) um item de keychain gerenciado por outro desenvolvedor, respeitando o modelo de segurança da Apple? Se não, qual camada impede isso e por quê?

### Takeaway
**INVIÁVEL, por design, em todas as camadas investigadas.** Não existe combinação de entitlement, API ou comando de linha que permita a um app de um Team ID (ou sem Team ID, no caso de assinatura ad-hoc) ler, sem prompt, um item de keychain pertencente/gerenciado por um binário de outro Team ID — nem mesmo pontualmente, porque o item do `claude` CLI é reescrito periodicamente (a cada renovação de token OAuth) e essa reescrita derruba qualquer ACL/partition list customizada que tenha sido concedida anteriormente via prompt aceito pelo usuário.

### Cited Findings
- Camada 1 — Entitlements de access group: barrados por Team ID, impostos por provisioning profile assinado pela Apple ("Keychain items can be shared only between apps from the same developer") — [Keychain Access Groups Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups)
- Camada 2 — API de ACL per-item (legada): deprecada sem substituto, e mesmo quando funcional exige autenticação do usuário para qualquer modificação cruzando identidade de processo — [Apple Developer Forums thread 129911](https://developer.apple.com/forums/thread/129911)
- Camada 3 — Ferramenta `security(1)`: só define apps confiáveis na criação do item; alterações pós-criação (via `-U -T` ou `set-generic-password-partition-list`) exigem prompt — [ss64 security(1)](https://ss64.com/mac/security-password.html); confirmado em casos reais — [Issue #438 cachix/secretspec](https://github.com/cachix/secretspec/issues/438)
- Camada 4 — Mesmo quando o usuário aceita o prompt uma vez ("Always Allow"), essa concessão é armazenada na ACL mas o **partition list** (um gate separado e **anterior** à avaliação da ACL, que não aparece na UI do Keychain Access) é resetado a cada reescrita do item pelo processo proprietário — tornando a concessão efêmera e reinstaurando o prompt no próximo refresh de token — [Issue #81707](https://github.com/anthropics/claude-code/issues/81707); [Issue #94491](https://github.com/anthropics/claude-code/issues/94491)
- Resposta explícita de um analista sobre esse exato cenário (app terceiro vs. item do `claude` CLI): "A third-party app cannot add itself to a keychain item's trusted list without prompting the user." — síntese derivada da leitura do Issue #77697 — [Issue #77697 anthropics/claude-code](https://github.com/anthropics/claude-code/issues/77697)

### Inferences
- A causa raiz, em todas as camadas, é a mesma decisão de design da Apple: **qualquer concessão de acesso cruzado entre identidades de código distintas (Team ID, ou ausência de assinatura válida) exige confirmação explícita do usuário**, e essa confirmação não é persistida de forma durável quando o item protegido é reescrito pelo processo proprietário — o que é exatamente o comportamento do `claude` CLI ao renovar tokens OAuth.
- Para o caso do ClaudeS (assinado ad-hoc, sem Team ID real), a situação é ainda mais fechada: mesmo as poucas vias que dependem de Team ID (access groups) exigiriam que o ClaudeS tivesse uma conta de desenvolvedor paga — pré-requisito que o ad-hoc signing não atende.
- Implicação prática para o projeto ClaudeS: qualquer solução sustentável terá que evitar depender de leitura direta do item de keychain do `claude` CLI sem intervenção do usuário. Alternativas fora do escopo desta pesquisa (não investigadas aqui) incluiriam: (a) pedir ao usuário para aceitar o prompt e orientá-lo a usar `security set-generic-password-partition-list` manualmente a cada renovação (inviável na prática, pois o reset é automático e frequente), (b) não depender do item de keychain do `claude` CLI e usar uma fonte de credencial própria do ClaudeS (ex.: `claude setup-token` com token de longa duração, mencionado no Issue #94491, mas com limitações: token apenas para inferência, sem conectores/agendamento/Remote Control, expira em 1 ano), ou (c) reportar/contribuir a correção a montante no repositório `anthropics/claude-code` para que o `claude` CLI preserve a ACL/partition list na reescrita — já há 3 issues abertos no repositório da Anthropic sobre exatamente esse problema (#77697, #81707, #94491).

### Gaps
- Não foi possível confirmar diretamente, com uma fonte primária da Apple, se o "partition list" é parte documentada publicamente da API Keychain Services moderna ou é um detalhe de implementação do keychain legado baseado em arquivo (`SecKeychainItemCreateFromContent` / ferramenta `security`) — a análise sugere fortemente que é este último caso (o `claude` CLI usa a API de keychain legada, baseada em arquivo, não a API `SecItem`/data-protection keychain moderna), mas não há uma página oficial da Apple que documente "partition ID" como conceito de primeira classe; a melhor fonte encontrada foi um artigo de terceiro (mostlikelee.com) e os próprios issues do GitHub, que descrevem o comportamento observado empiricamente.
- Não foi investigado neste research se existe algum mecanismo específico do macOS Sequoia/26 (2024-2026) que tenha mudado esse comportamento — a pesquisa não encontrou nenhuma nota de changelog recente da Apple revertendo ou alterando esse modelo; assume-se que o comportamento é estável desde pelo menos macOS 10.15 (Catalina) até as versões atuais (2026), mas isso não foi confirmado com uma fonte de changelog oficial de macOS 15/16.
