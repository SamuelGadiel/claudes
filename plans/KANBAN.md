## Investigated and discarded

- [x] **`security unlock-keychain` (the fastlane technique) to avoid repeated Keychain prompts**: discarded. `unlock-keychain` resolves lock/unlock for the whole keychain (already always unlocked in a normal graphical session) — a completely different problem from the per-item ACL that affects us. fastlane works in CI because it creates a new keychain and controls the ACL from the moment the certificates are imported; our case is reading an item the Claude Code CLI itself already created, with an ACL we don't control. Forcing something similar would weaken real security protection with no need — the packaged `.app`'s stable code signature already solves this correctly (authorizes once per account, never again).
- [x] **Automatic `git update-index --skip-worktree` on a versioned `.vscode/settings.json`**: discarded. Ignores the whole file, not just the `CLAUDE_CONFIG_DIR` entry — any other legitimate config someone added to that same file later would silently stop syncing.
- [x] **A separate workspace file (`.code-workspace`) outside version control**: discarded. Would require opening the project through that file instead of the folder as usual — changes a flow that already exists today (double-click, VS Code's "recent", Finder, Spotlight/Raycast), which the user doesn't want to change.
- [x] **An environment variable injected into the terminal before opening VS Code**: discarded. Only works when VS Code is opened via `code .` from a terminal — doesn't cover opening from the recent list, Finder, the Dock, Spotlight or Raycast, which are real flows for the user.
- [x] **Native VS Code profiles (one per account)**: discarded — the project had already discarded profiles from the start for a different, related reason (duplicating installed extensions), and creating a profile just for this config would reintroduce that exact problem: extensions, shortcuts and settings installed/changed in one profile don't automatically show up in the other.
